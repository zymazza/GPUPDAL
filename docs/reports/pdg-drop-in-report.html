PDG Drop-in Report

What PDG does for a PDAL user, in plain language: where it is faster, where it is not, and exactly what to expect when you run it on your own machine — including the parts we have not measured yet.

PDG is a fork of the pdal command line. You run the same commands and the same pipeline JSON (pdg pipeline job.json, pdg translate …). PDG preserves pinned PDAL 2.10.0 semantics: deterministic outputs, metadata, point order, stdout, stderr and exit status are compared byte-for-byte; inherently nondeterministic containers such as COPC use a separately versioned canonical semantic comparison. Current performance claims below come from the exact frozen 1.7× release artifact, not a rebuild.

The short version

  • For the current frozen 1.7× release artifact, seven of ten 1M r6 feature cells measured 7.4–10.2×. RTX 3060 and RTX 4090 measured 6.36× and 6.53×. The RTX 3090 is the explicit exception at 0.99×, not 2.5× and not 7–12×.
  • For the complete fourteen-workflow suite, current total-wall speedup ranges from 0.99× to 1.43× and equal-workload geometric mean from 0.98× to 1.18×. Older measurements of larger CPU-side gains remain historical and are not predictions for this artifact.
  • Nothing you get is approximate. Default mode preserves PDAL semantics: deterministic outputs are byte-identical, while inherently nondeterministic containers require canonical comparison. An opt-in pdg --fast mode relaxes only kNN tie order for a bit more speed.
  • The rule for switching a stage onto the GPU is a measured one: on each GPU class we ship, a stage is admitted at the point counts where the GPU beat PDG's own (already parallel) CPU path by at least 1.7× in our calibration, and stays on the CPU elsewhere. The first version of this report used a 3× rule; the maintainer lowered it to 1.7× the same day (see "What did not work" for why, and what it changed for the RTX 5090 and RTX 3090).
  • Not established: performance on GPUs outside the ten named classes, Windows, non-NVIDIA devices, the preregistered “≥10× on at least 90% of 3DEP projects” population claim, or unrelated third-party reproduction.

The promise, precisely

Three things are true of every run and are what the test suite enforces:

  1. Same pipelines. No new stage names, no options to learn. A PDAL pipeline JSON runs unchanged.
  2. Same semantics, with the comparator named. Deterministic output files, metadata, point order, stdout, stderr and exit code are compared byte-for-byte against a pinned build of upstream PDAL 2.10.0. Inherently nondeterministic containers such as COPC are canonicalized and compared by point records, metadata and semantics. Where a GPU path cannot reproduce PDAL exactly — for example a k-nearest-neighbour tie that PDAL's CPU tree resolves in one order and the GPU in another — PDG repairs the result on the CPU or does not use the GPU for that stage. Failures still fail with a non-zero exit and no output.
  3. Nothing tunes itself at run time. The decision "GPU or CPU for this stage on this machine" comes from a measured profile: the maintainer's reference machine, a profile you wrote with pdg calibrate, a profile we shipped for your GPU class, or a conservative generic one. PDG never times, fits or guesses while your job runs, so a given machine and input always makes the same choice.
pdg --fast (opt-in)Keeps point count, order, coordinates and every attribute except on exact-distance kNN tie rows, where the GPU's tie choice stands instead of being repaired to PDAL's. Rasters and text outputs stay byte-identical. When it was measured on the reference machine (before later exact-mode work) it ran the feature workflow at 11.6× against about 8.7× exact and the fourteen-workflow suite at 2.71× vs 2.61× geometric mean — a modest gain, because the exact tie repair is cheap. Exact mode has since improved to 2.90×; fast mode was not re-measured. It exists for users who prefer the simpler contract, not as the main speed story.

Does the ratio keep growing with bigger clouds or bigger GPUs?

No. We ran the same tile at 47M, 95M and 190M points on a rented H200 (141 GB): the kNN feature graphs sit on a flat ~10× plateau, ground classification climbs slowly (1.4 → 1.65×), and I/O-bound graphs stay at 1.4–3.6×. The H200 was not faster than an RTX 4090 in absolute time at these sizes. The GPU is not the bottleneck; single-file LAZ I/O, the exact CPU repair and CPU-only stages are. A larger card buys headroom (no tiling at 190M), not ratio.

What did not work, or does not help

Small clouds
Below about 250K points nothing runs on the GPU; CUDA start-up alone is 170–250 ms. Most stages need 1M points before the GPU wins by our margin, and several (normal, eigenvalues, covariancefeatures on their own) need 4M. Small-file batch jobs get the CPU-side speedups only.
filters.neighborclassifier
Loses on the GPU on every machine (0.3–1.3× against the CPU path). It stays on the CPU. Its CPU path is fast, which is why classification refinement is ~11× anyway.
Point programs — filters.assign, filters.ferry, filters.expression chains
Lose below 4M points, win modestly above. Shipped profiles admit them at 4M only; a lone filters.ferry almost never.
Ground classification (SMRF), height above ground, DTM/DSM rasters, tiling, merging, COPC queries, colorization, clipping, reprojection
1.0–2.5× from CPU work; the GPU is not used. Exact SMRF morphology on the GPU and GPU reprojection are on the follow-up list, unbuilt.
Forcing the GPU on
You can (PDG_EXPERIMENTAL_CUDA_HYBRID=1). On the boxes we measured, forcing the GPU everywhere was slower overall than the profile's choices (4090 box: 2.28× vs 2.51× geometric mean) because light workflows lose on the device. Leave it to the profile unless you are testing.
The 3× rule and the failed RTX 3090 expectation
The first shipped-profile proof used a 3× admission threshold; the profiles were then widened to 1.7× from calibration evidence. That historical analysis predicted the RTX 5090 1M feature graph and RTX 3090 large graph would improve when admitted, while continuing to describe the RTX 3090 1M r6 result as roughly 2.5×. The frozen-artifact rerun is now authoritative: RTX 5090 r6 measured 9.695×, but RTX 3090 r6 measured only 0.986× and its complete fourteen-workflow suite 0.987× by total wall. The report therefore records the 3090 as a current exception instead of preserving the calibration-based prediction.
Anything not NVIDIA, or below compute capability 8.0
No GPU use. AMD, Intel and Apple GPUs are not supported at all; NVIDIA cards older than Ampere (RTX 20-series, GTX, Turing/Volta data-centre parts) fall outside every shipped and generic profile. These machines get the CPU-side speedups and nothing else.

Things you will notice

  • Nothing to configure. If your GPU is in the shipped list, the first run already uses it where the profile says so. There is no flag to "turn on the GPU"; the profile does that per stage.
  • Which stages ran where. There is no friendly "explain" output yet — that is on the release list below. Today the diagnostic switches PDG_DEBUG_ADMISSION_PHASES=1 and PDG_DEBUG_HYBRID=1 print to stderr where an automatic GPU route was declined and why, and the benchmark harness records the active profile per run. If a stage you expected on the GPU ran on the CPU, the usual reasons are: point count outside the envelope, a layout the device path does not handle (it falls back, still exact), or a stage that lost the measurement (neighborclassifier, point programs below 4M).
  • Memory. Historical calibration/sweep runs exercised 48M-point LOF and feature graphs on selected 24 GB cards and stopped the 12–16 GB profiles at 16M. The current frozen B0286 proof is narrower: one 47.5M AHN4 r6 graph on seven named machines at roughly 10–15 GB peak host RSS. Above every admitted envelope PDG does not "try anyway".
  • Files with vendor extra dimensions (e.g. AHN4's Deviation, Amplitude, Reflectance) now run on the GPU path as long as no GPU stage computes those dimensions; a file that carries a device-computed dimension in an unexpected type (e.g. Rank=uint16 under filters.estimaterank) is refused by the device path and completes on the CPU under the same deterministic-byte/canonical-container contract.
  • Container CPU quotas matter more than the GPU. Every rented box had a cgroup quota of 9.6–30.7 cores. Both PDAL and PDG scale with cores, so ratios are fairly stable, but absolute times on your workstation will differ from the boxes'.
  • Determinism. Same machine, same input, same profile → same placement; deterministic outputs reproduce the same bytes, while containers known to be nondeterministic are evaluated canonically. Run-to-run wall time varies by ±10–20% on I/O-bound workflows on the rented boxes; that is noise, not placement change.

When to run pdg calibrate

You do not have to. Run it when (a) your GPU is not in the shipped list and you want more than the generic tier, (b) your CPU is much faster or slower per core than an EPYC/Xeon server part — a fast desktop CPU narrows every GPU margin — or (c) you want placement tuned to your own data (--input your-tile.laz; the synthetic calibration cloud under-represents filters.radiusassign on real data). It takes 17–41 minutes for the standard sizes on the boxes we used, plus 6–72 minutes for the optional 16M/48M append; it writes ~/.config/pdg/placement-profile.json (or $PDG_PROFILE_PATH), only ever admits stages whose device output was byte-identical to the CPU's, and its profile is keyed to your exact machine, so it cannot be copied to another. --status and --dry-run write nothing.

Testing it yourself

  1. Check the tier: pdg calibrate --status. If you expected shipped and see generic or nothing, check the GPU name (must match exactly, e.g. NVIDIA GeForce RTX 4090), compute capability, and that PDG was built against CUDA 13.3.
  2. Prove exactness on your own data: run the same pipeline with pdal and pdg and compare deterministic LAS/LAZ and rasters bit-for-bit; use the versioned canonical comparator for a COPC container whose oracle bytes are themselves nondeterministic. This is what the conformance suite does with a pinned PDAL 2.10.0 build; an unexplained default-mode semantic difference is a bug — please report it with the pipeline and a small input.
  3. Measure fairly: warm the cache (run once, discard), take the median of three, and compare a PDAL and a PDG built the same way on the same machine. Our harness is scripts/pdg/benchmark_reference.py (paired runs, byte comparison, per-run profile record) and the fourteen workflows are in bench/pipelines/reference/. Wall time is the whole process, read and write included.
  4. Do not assume a universal gain. If a kNN pipeline at 4M points shows no gain on a shipped GPU, inspect the active tier and placement diagnostics: the point count may be outside the admitted envelope, the layout may be unsupported, or the stage combination may be unprofiled. Report an unexpected result with those diagnostics and a same-machine PDAL baseline.
  5. Big inputs: the current 47.5M frozen-artifact r6 proof covers exactly seven named classes—A10, A100 40 GB, L40S, RTX 3090, RTX 4090, RTX 5090 and RTX A6000—and measured 6.81–11.60× with three pairs per cell. It is not evidence for the three smaller cards or for all ten classes. Watch host RAM (~10–15 GB peak for the tile).

Before you release it: what an open-source audience needs to know

These are the facts a README, release note and issue template should carry, and the loose ends we would close or state first.

  • The shipped profiles are keyed to CUDA toolkit 13.3. A build against 13.4 (or a distro/conda package built with another toolkit) gets no shipped and no generic tier — CPU path only until someone runs pdg calibrate. Either re-sweep on the release toolkit, relax the key deliberately with new measurements, or say it plainly in the install docs. This is the single most likely "it's not using my GPU" report.
  • Binaries must carry the right GPU architectures. The sweep boxes were each built for their own SM (80/86/89/120; 90 for Hopper). A distributed build needs a fat binary covering all of them, or the shipped tier is moot on the ones left out.
  • Local profiles are keyed to the PDG version. A version bump silently invalidates every user's calibration (they fall back to the shipped tier). Say so in release notes and consider a "profile out of date, re-run pdg calibrate" hint in --status.
  • State the hardware support honestly: NVIDIA only; shipped profiles for the ten listed classes; conservative generic placement on other Ampere-or-newer cards ≥ 12 GB; no GPU below that. Do not promise a universal CPU-side gain: the current complete-suite totals range from a 0.987× loss to a 1.430× win across the measured hosts.
  • The exact 1.7× artifact has now been re-run. The current table binds the candidate, oracle, profile files, harness, pipelines and inputs by SHA-256, checks the payload before and after timing, and never rebuilds on a benchmark worker. The older 3× tables remain labelled historical.
  • Measurements are one warm-up plus three paired observations on rented containers with CPU quotas: all ten classes at 1M and only the seven named classes at 47.5M. Publish the raw JSON and host facts with every number; do not generalize the 47.5M result to the three untested cards.
  • Unmeasured: the generic tier on any big cloud; H100/H200 under the generic tier (an H200 was measured only with CUDA forced on: ~10× plateau); Windows and macOS (nothing built or run); non-x86 hosts; the "direct whole-view" GPU executors off the reference machine (they stay CPU elsewhere).
  • Known follow-ups: run the preregistered 40-project 3DEP population study; obtain unrelated-user reproductions; build exact SMRF morphology on the GPU, GPU reprojection, LAZ encode scale-out for wide records, a profile refresh protocol, and calibrated direct executors.
  • A plain "why did this run on the CPU?" output. Users will ask; today the answer needs two debug variables and knowledge of the envelope table. An --explain-style summary of per-stage placement and the reason would prevent most support traffic.
  • Housekeeping: the repository README is still upstream PDAL's; write PDG's own (what it is, the promise, the tier table above, how to check and calibrate, how to report a wrong placement). Decide the licence stance for the fork and the shipped profile data files (they are measurements, in JSON, under data/placement-profiles/). Keep the "regenerate, never hand-edit" rule for those files.
